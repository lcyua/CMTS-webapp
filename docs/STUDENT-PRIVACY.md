# 학생정보 관리와 보안

## 준비 상태와 확인 범위

이 문서는 학생정보 관리의 **소스 구현과 가상 검증**을 설명합니다. 이름·학번 편집 기능은 실서비스 Worker·Hosting에 아직 배포하지 않았습니다. 검토 화면에는 가상 학생 18명만 사용하며 실제 학생정보를 넣지 않습니다.

전체 단위 검사 150개가 통과했고, 학생프로필 전용 합성 검사 13개가 포함됩니다. 실제 로컬 Firestore Emulator의 7개 통합 그룹에서 학번 매핑의 원자적 변경·복귀도 확인했습니다. 프로젝트는 `demo-worker-firestore`, 접속은 loopback으로 제한했고 생성한 합성 문서 1,219개를 모두 삭제한 뒤 조회로 확인했습니다. 실제 학생정보·실서비스 credential 문서·원본 시트·기존 PIN 전달 파일을 조회하거나 변경하지 않았습니다.

## 이름·학번 수정

- 현재 활성 교사만 수정할 수 있습니다. 학생 UID·역할·계정 자체는 편집하지 않습니다.
- 이름은 앞뒤 공백을 제거하고 길이를 검사합니다. 학번은 앞자리 `0`을 보존하는 숫자 문자열이며, 비활성 학생을 포함한 다른 학생의 학번과 중복될 수 없습니다.
- `profileVersion`과 수정 전 학번을 함께 검사해 오래된 화면이 최신 정보를 덮어쓰지 못하게 합니다.
- 이름만 바꾸면 로그인 credential을 읽지 않습니다. 화면의 이름은 학급 프로필을 기준으로 하며 Firebase Auth 계정은 변경하지 않습니다.
- 학번을 바꾸면 기존 UID·salt·AuthEmail·PIN의 파생 결과를 유지합니다. 새 학번의 로그인 매핑, 이전 학번의 폐쇄, 학급 프로필, 감사·요청 영수증을 같은 Firestore CAS commit에 반영합니다. 추가 Auth 관리 권한이나 PIN 재발급은 필요하지 않습니다.
- 이전 학번의 매핑은 salt·AuthEmail이 없는 비활성 tombstone이 됩니다. 같은 학생 UID에 대해 생성한 정확한 tombstone일 때만 원래 학번으로 되돌릴 수 있으며, 다른 계정의 매핑은 차지할 수 없습니다.
- 기존 포인트·역할·배치·신청은 UID로 연결되므로 유지합니다. 과거 신청 등에 당시 이름·학번을 복사해 둔 기록은 당시의 스냅샷으로 남기고 일괄 덮어쓰지 않습니다.

## 화면에 공개하는 범위

교사와 학생 본인의 member 응답도 필드 허용목록으로 만듭니다. 이름·학번·역할·활성 상태·위임·프로필 버전 등 화면에 필요한 정보만 반환하며, 알림 설정은 `enabled`만 반환합니다. salt·AuthEmail·PIN·비밀번호 같은 필드는 응답에 포함하지 않습니다.

다른 학생에게는 학급생활 화면에 필요한 UID·이름·역할·활성 상태만 반환하고 학번은 숨깁니다. 학생의 포인트·신청·답안·시험·알림 기록은 본인 것만 반환하며 감사 기록은 교사 권한으로 제한합니다. 웹 클라이언트의 Firestore 직접 읽기·쓰기는 거부하고 Worker에서 인증·학급 소속·역할을 검사합니다.

현재 비로그인 로그인 화면은 활성 학생의 **학번 선택 목록**을 제공합니다. 이름·UID·PIN은 포함하지 않지만 학번 자체는 익명 사용자도 볼 수 있습니다. 공개 범위를 더 줄이려면 학번 직접입력 방식으로 전환하는 것을 권장합니다. 전환 여부는 사용자 선택 대기이며 현재는 학번 선택 목록이 공개된 상태입니다.

## 비밀번호와 PIN

사이트에서 기존 비밀번호/PIN 원문을 조회하거나 표시하는 기능은 제공하지 않습니다. 서버 전용 pepper와 계정별 salt로 파생한 긴 값을 Firebase Auth가 해싱·검증하며, 클라이언트에는 이 값이나 salt·pepper를 보내지 않습니다. 이름·학번 편집은 기존 18명의 계정과 PIN을 유지합니다.

**현재 PIN 변경·재설정 버튼과 endpoint는 구현하지 않았고 실제 재설정도 하지 않았습니다.** 향후에는 학생 본인의 재확인 또는 교사의 확인을 거친 개별 변경·재설정 절차로 준비해야 합니다. 기존 PIN을 보여주는 방식이나 전체 학생 일괄 재발급으로 대신하지 않습니다.

PIN을 일반 `command`의 입력에 넣으면 안 됩니다. 일반 명령은 입력을 감사·요청 영수증에 보관하므로 평문 PIN이 감사·백업에 남을 수 있습니다. 변경 기능은 전용 민감 경로, 본인·교사 권한 재검사, 시도 제한, PIN·토큰·credential 메타데이터가 없는 감사 기록과 실패 복구 절차를 별도로 설계해야 합니다.

네 자리 PIN은 조합이 1만 개로 제한됩니다. 현재는 학번별 5회·IP별 50회의 실패/진행 중 시도를 15분 창에서 제한하고, 자격증명 실패는 ‘학번 또는 비밀번호가 일치하지 않습니다’라는 일반화된 오류로 안내합니다. 이 제한이 긴 비밀번호나 학교 계정 인증과 같은 보안 수준을 보장하지는 않습니다. 향후 강화 방식은 기존 PIN을 임의 변경하지 않고 별도로 결정합니다.

## 보관과 복구

기존 PIN 전달 파일은 운영자가 별도로 보관합니다. 사이트 배포·Git·공개 ZIP·공유 백업에 넣지 않고 접근 권한이 제한된 비공개 보관 방식을 사용합니다. 현재 학급 백업 도구도 Auth·`pinAccounts`·PIN 전달 파일을 읽거나 복원하지 않습니다.

학번을 바꾼 뒤 과거 백업과 현재 명단의 학번이 다르면 기존 복구 도구는 identity 불일치로 안전하게 중단합니다. 복구 전에 현재 로그인 매핑과 복구 범위를 함께 확인해야 합니다. 이 검사를 자동 우회하거나 학생 계정·PIN을 재생성하지 않습니다.
